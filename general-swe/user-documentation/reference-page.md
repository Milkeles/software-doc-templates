# Reference Page

> The information on the back of the packet. Complete, accurate, and boring on purpose.
>
> **What it is for.** Describing the machinery. Procida's summary of the type: it exists "to describe the machinery", it answers "What is…?", and its form is "dry description". A reader arrives knowing what they want and needing one fact.
>
> **The one quality that matters.** Correctness. Uddin and Robillard surveyed 323 software professionals for *IEEE Software* (2015) and found the three severest documentation problems were "ambiguity, incompleteness, and incorrectness of content", concluding that "the most pressing problems were related to content, as opposed to presentation". Six of the ten problems they catalogued were rated blockers that pushed developers to a different API.
>
> **Generate it wherever you can.** Hand-written reference is wrong within two releases. Anything derivable from source, schemas or an OpenAPI document should be derived.
>
> **Where it lives.** Docs-as-code, next to the thing it describes, ideally generated by the build.
>
> **Delete this block before publishing.**

---

## 1. Structure is the product

A reference page is used by scanning, not reading. The reader knows the answer exists and is looking for where it sits on the page.

**Every page of the same kind gets the same headings in the same order.** Consistency is not tidiness here; it is the mechanism by which the page is usable. A reader who has read one function page knows where the return value is on all of them.

Pick the field order once, write it down in the [style guide](documentation-style-guide.md), and never vary it.

---

## 2. Field order for a function or method

| Field | Notes |
|---|---|
| Signature | Exact, copyable, with types |
| Summary | One sentence. What it does, not why |
| Parameters | Name, type, required or optional, default, meaning, constraints |
| Returns | Type and meaning, including what an empty result means |
| Raises or errors | Every error it can produce, with the condition |
| Since | Version introduced. Deprecations flagged here |
| Example | One minimal, runnable call |
| See also | Neighbours and the how-to guides that use it |

The two fields most often missing are **constraints** and **errors**, and they are the two a reader most often came for. A parameter documented as "the timeout" is not documented. A parameter documented as "timeout in milliseconds, 1 to 300000, default 30000, values above the server limit are clamped silently" is.

---

## 3. Field order for an endpoint

| Field | Notes |
|---|---|
| Method and path | `POST /v1/keys/{keyId}/rotate` |
| Summary | One sentence |
| Path and query parameters | As above, with constraints |
| Request body | Schema, with every field's type, requiredness and constraints |
| Responses | Every status code, with body schema per code |
| Errors | Codes and their meaning. Link the error format |
| Idempotency | Whether retrying is safe, and how |
| Auth and scopes | What the caller needs |
| Rate limits | If any apply |
| Since and stability | Version, and whether the shape can still change |

See [`../../web-development/foundations/api-design-guide.md`](../../web-development/foundations/api-design-guide.md) for the conventions these pages document.

## 4. How to write the prose

There is very little of it, and that is correct.

**Describe, do not instruct.** "Returns the active key" belongs here. "Rotate your key every 90 days" does not; that is a how-to guide or an explanation.

**Present tense, active voice, no hedging.** "Returns null if no key exists", not "will normally return null in cases where no key may exist".

**Never explain the design.** The reasoning is legitimate and interesting and belongs in [`explanation.md`](explanation.md). A reference page that argues its own case has stopped being scannable.

**State what happens at the edges.** Empty input, null, zero, the maximum, concurrent calls, the value after a failure. These are the questions that send people to read the source.

---

## 5. Generated versus hand-written

Generate: signatures, types, parameter lists, schemas, status codes, enum values, defaults. Anything that exists in the source is a duplicate the moment you retype it.

Hand-write: the summary sentence, the meaning of a parameter beyond its type, constraints the type system cannot express, the examples.

**The two must live in the same file.** Docstrings, schema descriptions and OpenAPI `description` fields keep the prose next to the thing it describes, so a change to one is a visible change to the other. Prose in a separate document diverges, and nobody notices until a reader is misled.

Where generation is impossible, add a check that fails the build when the two disagree. A test asserting that every public function has a documented return value is cheap and catches the whole class of omission.

---

## 6. Completeness

Reference is the one type where completeness is genuinely the target. A how-to guide covering 80% of tasks is useful. A reference covering 80% of parameters sends readers to the source and keeps them there.

Track it. A count of undocumented public symbols, published and trending toward zero, does more than a style rule.

**Document deprecated items rather than deleting them.** A reader hitting a deprecated call needs to know what replaced it. Mark it, date it, link the replacement, and see [`../foundations/deprecation-plan.md`](../foundations/deprecation-plan.md).

## Common failures in this document

- **Inconsistent field order.** Every page must be read rather than scanned.
- **Types without constraints.** "string" tells the reader nothing they could not see from the signature.
- **Undocumented errors.** The reader discovers the failure modes in production.
- **Explanation smuggled in.** Turns a lookup table into an essay.
- **Hand-maintained copies of generated facts.** Diverge silently and mislead confidently.
- **Silent gaps.** An undocumented parameter looks identical to one that does not exist.
- **Examples that do not run.** Copy the example into a test.
